# FinLab／FinMind 請求排程實測與修正（2026-10-24）

本次沿用兩個來源原有的帳號、下載器、佇列與收據。目標是讓必要工作持續供給下載管線，降低啟動、排程與進度計算的成本；配額、來源供應、驗證、落盤與資料完整度仍各自驗收。

## 工作量與限制

- FinMind 帳號實際回報 SponsorPro、20,000 次／小時，符合[官方方案](https://finmind.github.io/Pricing/)。三條既有下載服務共用帳號配速與請求帳本，不能各自另算 20,000 次。
- FinLab 本次帳號快照為每日 5,000 MB，按官方帳號回報核算。來源傳輸位元組與本機 Parquet 大小不同；不能用壓縮後檔案大小冒充 API 用量。SDK 追新保留既有本地預留豁免，但來源的配額與認證錯誤仍會停止請求。
- 台股交易日、表定發布時間、當小時追新預留及重試狀態繼續參與每次派工。FinMind 保留既有九階段順序及美股分鐘 K 最後的設定。
- FinLab 仍先一般歷史資料、再分鐘、最後剩餘流量的 tick；分鐘 32 個工作者，tick 8 個工作者。原有單日 tick、分鐘日期窗、50 MB 分鐘預留與重置前消耗政策均保留。
- 來源尚未上架的候選日期與已驗證空回應不算資料完成；增加執行緒不能產生不存在的觀測。WSL 25 GiB 容量保護保持原設定。

吞吐量取決於共享 API 額度、網路傳輸、解析驗證、持久化、以及排程供給中最慢的一環。這次測試分別量測本機排程和真實 SDK 處理，沒有把局部加速換算為整體歷史下載倍數。

## 實作

### FinMind

1. 在既有 Complement owner 一輪執行期間重用唯讀 SQLite 連線。每次仍重新查詢已提交的工作，不保留跨請求的排程結果，也不持有跨派工的讀取交易。
2. 日曆、來源收據和服務狀態只在檔案裝置、inode、大小、mtime_ns、ctime_ns 全部相同時重用解析結果。每次檢查檔案身分；新佇列、資料庫替換、破損檔案與異常結束均有測試，沒有固定 TTL 延遲。
3. 將歷史候選查詢的兩個日期界線都綁到 frontier 外層資料，使 SQLite 使用既有 `(dataset,data_id,partition)` 索引的雙界線搜尋。保留 TAIEX 的 2005 年特殊起點、休市日排除與已排入工作扣除。
4. JSON pipeline 升為 v13，讓 ETA 重新校準，避免混入 v12 的容量樣本。仍需完成整輪、成功驗收、設定指紋一致的樣本。
5. 沿用原安全重載工具，新增對本次完整本機排程測量的校驗；檢查輸出一致、ABBA 順序、程式雜湊、實際時間與佇列未變更。只有原服務無請求、零 claim 的邊界才允許採用。
6. 找到每分鐘配額服務的另一個成本：完整 ETA 在原生環境每輪約 40–46 秒 CPU。由原佇列 owner 維護兩個覆蓋索引，讓工作分類只讀必要欄位、近期成果按時間搜尋。先以兩次有序聚合取代全量排序，再實測改為取得少量分類鍵、對各分類的到期／未到期／空時間範圍計數並尋找極值。每筆任務仍參與計數，配額仍每分鐘取樣，完整預估的內容與頻率均保留。
7. 下次喚醒不再計算所有未來任務的全域最小時間，改用原有 `(priority,next_attempt_at_utc,state)` 索引，逐優先序搜尋最近時間。沒有新增等待、提早重試或縮短來源封鎖；舊索引缺少或結構不符時維持原查詢。
8. 新索引只儲存必要的 SQLite 鍵，在同一任務交易內維護，不複製來源 Parquet，也沒有另一個統計服務或固定 TTL。真實快照兩個佇列合計增加約 **0.876 GiB**；額外持久寫入成本一併量測。
9. 修復跨管線等待：Free 的工作以收據排程，沒有 `tasks` 佇列；原喚醒程式只讀 SQLite 重試時間與日曆，可能在兩筆追新已到重試點時繼續睡眠，讓其他 owner 因追新優先而停住。現在 Free 依同一組追新收據的期限喚醒；若規劃期間剛跨過期限，最多再等一秒。來源原有的一小時空回應冷卻、429／IP 封鎖及盤前保護均保留。
10. 日曆每次派工只格式化一次日期界線，避免對 5,408 個日曆項目逐一重複格式化相同日期。等待心跳另記錄實際載入的 runtime SHA，便於區分磁碟上的新程式與仍在執行的舊程序。
11. 非空 JSON 回應原先先同步暫存 Parquet 的資料與目錄，再由 `durable_replace` 重複同步相同資料並發布最終檔名。現在暫存僅作原子寫入準備，仍由原有最終發布完成資料與目錄同步，之後才能發布來源更新觀察與持久收據。已存在且 SHA 相同的最終 Parquet 保留原 inode，碰撞修復仍走原有耐久替換。全域原子寫檔工具的預設、佇列交易與其他下載器均未改動。
12. 發布成本改變後，JSON pipeline 升為 v14，設定指紋更新為 `b8e1959364e2290c5906aff6c604a93bff4cbbe6e748c381fa7bfdfcbca920b2`，讓 ETA 排除舊版容量樣本。工作者數、1 GiB 最壞回應記憶體上限與每輪 1,200 次工作量保持原設定。
13. 接續採樣找到追新預留的剩餘查詢成本：舊查詢的執行計畫只依 `priority` 搜尋，仍掃描全部最高優先工作。沿用原有部分覆蓋索引，將「待處理且時間為空」與「有效狀態且期限內到期」分成互斥的兩段，再依原欄位合併計數。現在兩段都使用 `priority/state/time` 界線；來源／重試 cohort、當小時預留、派工及舊結構 fallback 保持原語義。沒有新的實體索引或資料快取。
14. 範圍搜尋採用 v15 與設定指紋 `322bfc25ea4dd419e83cdddd4c818b02c8316b093076f142a746a05b203692cb`，再次分離實際部署後的容量樣本。原基準工具增加捕捉舊／候選查詢的模式，兩邊都重用正式連線範圍、相同 frontier 與相同 frozen queue，不用不同連線策略冒充 SQL 本身的改善。
15. 原生 v15 採樣仍有約 18／44.1 秒主執行緒時間在資料發布，另有 claim/release 成本。JSON pipeline v16 讓兩個獨立鍵平行執行原 `_store`，SQLite 工作選取、claim、結果確認和釋放仍只由原 owner 寫入。發布中的回應保留原槽位，下載、已完成回應與發布合計仍受原 16 個槽位／1 GiB 最壞回應界線約束；來源寫入及收據完全耐久後才更新佇列。結束或例外時先等待發布池，再關閉帳號資源，未確認的 claim 繼續走原恢復。
16. 發布工作各自繼承獨立 Decimal context，沒有降低金融精度。設定缺少 `publication_workers` 時維持序列舊行為，正式選用已實測的 2；新設定指紋 `5507e709891e0c3b9fcf91571cb2a213b0486455efbb00bf1ff1089202bd846d` 分開重測整輪容量。採用工具另核對正式磁碟裝置、同一次開機、八次 ABBA 的耐久輸出／原 inode／單一佇列寫入者與目前程式 SHA。

來源值、單位、非空變空保護、來源與收據 SHA、錯誤重試上限、429 退避及全帳號追新優先權均沿用原下載器。

### FinLab

1. 一般資料每個 SDK 程序由 8 張改為 32 張，攤薄 Python／SDK 啟動及全目錄規劃成本。
2. 保留逐表 600 秒期限、連續兩次逾時退出、每表記憶體釋放、不相容 SDK 改走程序隔離，以及逐表開盤資源時窗檢查。沒有把 32 張表一次留在記憶體中。
3. 設定與 Bash 都驗證批次範圍為 1–64，目前正式設定選用已實測的 32。盤前模式仍使用單表與完整期限的開盤前 runway。
4. 既有 SDK ABBA 工具新增可設定的匹配組大小、原 writer lock 有界等待及來源 Parquet 雜湊一致性驗證；不另外建立下載管線。
5. 原包裝器的研究重建、發布與冷恢復驗證可能占十多分鐘，且排在分鐘下載之前。最終改為 **一般表 → 分鐘 → 剩餘配額 tick → 原研究重建／發布**。沿用同一 writer lock、所有來源雜湊／發布／恢復驗證與 tick 的逐次派工檢查；分鐘失敗或未清空時不啟動 tick。研究硬錯誤仍讓服務失敗並保留證據，已獨立完成的原始資料不會因此失去收據。
6. 實際日誌確認，只把分鐘移到研究前仍會延誤 tick 檢查：00:23 分鐘已清空，但研究及冷恢復驗證一直到 00:41。輪到 tick 時另有 221 筆分鐘重查到期；不過 tick 的終止狀態是 `waiting_older_publication`，不是 `waiting_required_minutes`，不能把零請求直接歸因於分鐘優先權。將所有來源下載排在研究前可消除這段打包等待，不能據此宣稱來源已供應更多舊歷史。
7. 冷稽核沿用已註冊 D 主庫的原生 Windows 讀取介面，完整讀取相同 blob、pack、chunk 並核對雜湊／成員；僅限標準主庫及有效 enrollment marker，其他路徑保持原讀法。沒有略過驗證、複製整份快取、改寫來源或把本地驗證當成遠端恢復。
8. 實際 systemd 採用暴露環境差異：`stockagent-data` 只初始化自己的子程序，父程序後續啟動的原生稽核仍缺 Windows PATH／bridge。稽核前改用既有 `ensure_enrolled_wsl_identity`，同樣驗證已註冊身分；環境或完整性錯誤依舊回傳非零，不以 fallback 掩蓋。原失敗日誌保留，另以原服務完整稽核收據驗收。

完整 ETA 比較涵蓋 106 個已註冊資料集。喚醒時間計算是索引與喚醒那一列的子集，從中位約 1.81 秒降到 0.009 秒，結果相同，不能再和整體倍數相加。第一版只加索引的完整對照為 48.60→28.29 秒，仍有大量分類排序，因此繼續改寫聚合。各輪快照、觀測時間與共享主機負載不同，不把不同輪次直接相減或相乘當成整體收益。

並行發布最初在 `/tmp` 測得約 1.09 倍，但該路徑為 tmpfs，只保留為資料一致性診斷；正式採用改用 `/var/tmp` 的 ext4，逐次核對與正式佇列相同裝置，完整測量為上表的 10.39→6.13 秒。八輪各處理 96 次真實原生 store／claim／release，HTTP 使用先前已取得且 SHA 保持的 240 筆回應；沒有為了基準重抓來源或改寫正式資料。正式網路吞吐另做原生週期驗收。

索引比較另做 4 次、每次 32 筆任務／64 次原生 durable claim/release 交易，逐筆確認回復原值。第二輪兩組中位持久寫入 wall time 約 1.03／1.01 秒，CPU 約 0.040／0.048 秒；共享主機的 I/O 變異明顯，僅用來揭露額外成本，不宣稱寫入加速。第一次建立索引約需 8 秒（Sponsor）及 147 秒（Complement），是一次性設定成本，沒有藏在每分鐘 ETA 的數字中。

FinMind 比較包含原生 `StatusConnection` 的每輪首次統計與後續快取，沒有省略正式服務的進度輸出。原先誤用一般連線的試驗由操作者中斷，保留失敗紀錄；其結果不作為驗收。快照複製與測試設定成本另列於 agent run receipt，沒有算成下載管線的節省。

FinLab 比較包含真實 SDK 檢查、全目錄規劃、轉換／完整性判斷、收據與程序 wall time。這是小型既有表的追新測試；不代表所有大表、分鐘與 tick 都可加速 1.69 倍。ABBA 降低順序影響，但共享主機負載和快取效果仍存在。

發布同步另以同一來源分鐘回應的 353 筆資料建立 48 個明確標記的測試識別碼，每次完整執行首次發布、相同內容追新、Parquet footer／完整 SHA 回讀及收據核對，共 96 次 `_store`。每輪只使用程序專屬暫存目錄，沒有 API 呼叫、正式佇列或來源修改。原生檔案同步次數由 **576 降為 384（少三分之一）**；其中最終資料仍為 48 次同步，收據仍為 144 次同步，相同最終檔案的 inode 均保持。

第一輪八次 ABBA 的中位 wall time **9.83→14.85 秒**，並未通過採用門檻，原始負面結果保留。為分辨 I/O 爭用與程式成本，第二輪增加每次實際 fsync 計時，同樣八次 ABBA 得到 **17.14→6.48 秒**，兩邊各四次完整輸出 SHA 一致。兩輪十六次合併中位為 **12.39→10.80 秒**，這項觀察仍不足以保證固定加速倍率；測試時主機有其他 CPU／磁碟工作，第二輪耗時主要落在實際同步等待。

較早的四執行緒獨立發布原型，局部中位 19.92→11.08 秒，輸出與既有檔案保持；這個四執行緒原型未部署。先移除重複同步，再以完整佇列與狀態路徑驗證兩個有界發布工作；後者才是 v16 的採用範圍。補充的故障測試確認：最終檔案同步失敗時不發布來源觀察、不替換舊收據，也不破壞舊非空 Parquet。

最後一輪相關回歸 **2,020 項通過，265.57 秒**，涵蓋 FinMind v16、FinLab 來源順序、完整冷稽核路由與原生讀取介面。後續無人值守初始化修正的聚焦驗證另為 **150 項通過，35.58 秒**，與完整回歸有重疊，不能相加。發布候選與採用門檻另有 137 項聚焦驗證。Bash 測試實際執行包裝器，覆蓋研究建置／staging／發布的預期暫緩及硬錯誤、分鐘清空與未清空、tick 最低優先序，以及 Windows 環境初始化成功或失敗。喚醒與預留查詢另以 SQLite 執行步數驗證不再遍歷全部未來工作，並保留空時間、空優先序、終止狀態、重試 canary 及舊結構的結果。並行測試驗證相同原始值、Decimal context、單一佇列寫入者、耐久收據先於確認、回應槽位背壓、來源更新觀察與失敗恢復。

## 正式採用與限制
