# FinMind 最長區間與最少請求 — 2026-09-27

## 原理與邊界

5 年不是已查到的官方上限，而是舊版下載器的本機保護值。官方
[OpenAPI](https://api.finmindtrade.com/openapi.json) 沒有公布統一最大年數或回應列數；
這不代表官方保證無限。現在對已驗證的區間端點，合併最長連續必要待抓區間，
從來源最早日期到所需終點，不因 2014 訓練起點切成更多 HTTP。

「最少」必須同時滿足：端點支援區間、目前帳號具權限、保留增量配額、
回應可完整處理、不重抓已完成區間、不越過冷卻／在途工作。不同 dataset 不能
假裝合成一個官方請求。全市場單日端點仍逐日；SDK 多股票迴圈不是單次批量 API。

## 真實長區間驗證

這是 8 次一次性資料 API 驗證，不是 8 次新增歷史落盤；沿用共享配額與限流。
對已完成本機分區核 SHA 後，回應投影欄位的逐列／重複次數比對均一致，
沒有越界日期。舊版驗證只比較回應中的欄位，不能排除整欄消失；新版 probe
另外檢查新舊 schema。上游沒有提供總筆數，故不是全史無缺漏證明。

## 已實作

- `finmind_batching.py`：8 個 allowlist 來源無固定年月上限；不跨完成、冷卻、
  缺口、在途或 P3 純校驗工作。原子 claim，整批所有日期驗證通過才分區存檔。
- 保留原 queue／Parquet／receipt；每個分區記錄同一 `request_id`、整批筆數、
  分區筆數及查詢邊界，不把一個 HTTP 誤算成數十次。
- 解碼後 HTTP body 上限 64 MiB、100 萬列是本機安全值，**不是官方上限**。
  JSON 解析後的物件及 Parquet 轉換另有記憶體成本，不宣稱程序 RSS 僅 64 MiB。
- 超大回應／確定的讀取逾時／502、504 才記錄縮半的批量上限，60 秒後重試；
  不永久停用區間。真正契約不符才隔離合批、保留單分區路徑。
- 正確辨認 requests 把串流 ReadTimeout 包成 ConnectionError 的情況；
  不因錯誤文字含 timeout 就把任意連線錯誤當成容量不足。
- 背景配額不足時只放行原增量任務，不偷偷夾帶多年歷史。`--dataset` 只限縮
  同一 canonical worker 的派工範圍；仍遵守共享鎖、預留及全域 P3 門檻。
