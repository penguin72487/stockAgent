## 統計口徑與異常

- 天數是非空資料的相異日期數，不是起訖相減，也不是股票數乘天數。
  原歷史摘要新增 `tick_data_days` 等欄位；原 `tick_dates` 仍代表合約日分區，沒有改義。
- FinMind 期權的日分區依事件日期；TAIFEX 與 Shioaji 期權依交易日包含前一晚夜盤。
  相同起訖或天數不能直接解讀成同一範圍。
- 指數 Tick 為指數報價；每秒五檔為衍生快照，均與逐筆成交分開。
  FinMind `TaiwanFutOptTickInfo` 是代碼表，不是歷史成交。
- TAIFEX 的滾動 manifest 只列近期；本次 footer 清點保留全部 82 個實存日期。
  TXO 的列是買賣側明細，不等於去重後的成交次數。
- capture 的日／夜盤及頂層 worker 鏡像沿用正式選取規則，不重算鏡像；
  只計 `rows_written`，不把排隊事件或零筆未來日期算入存量。
- 另保留未配對目前 capture 清冊的舊分片，分類獨立列出，沒有併入主清冊。
  尚未讀完時顯示已知筆數／天數下界與待清點目錄數；讀不出的檔案維持異常，未知不當作零。
  完成清點後有 17 個期權成交分片、19 個五檔事件分片、21 個每秒五檔分片無法讀取，
  共 57 個且都確認是 0 bytes；原檔保留。
  [完整錯誤明細](../artifacts/data_quality/tick_inventory_2026-10-25/unreadable_capture_files.json)。
- 收據索引未重新驗證所有原檔 SHA；起訖最早／最新不代表中間沒有缺口，
  五檔也不能由事後歷史 Tick 重建成未錄到的真實委託簿。
- 未提供／未啟用的海外、外匯與 crypto Tick 仍有登錄與原因，筆數為未知。
  未因此新增交易所或啟用 crypto Tick 下載。

## 維護與效能

沿用 `stockagent-data-refresh-status-snapshot` 作為正式快照發布 owner，
以 `stockagent/live/tick_inventory.py` 組合既有收據；沒有新增 API 下載管線。
來源檔案身分未變則重用快取，SQLite WAL 變動會使對應統計失效。
FinLab 查詢限制為 Tick 的既有複合主鍵範圍，避免掃描所有分鐘分區。

無 WAL／journal 且讀取前後檔案身分相同時，才容許 SQLite `immutable=1`
讀取已 checkpoint 的單檔，解決唯讀 systemd mount 不能建立 sidecar 的問題。
既有 WAL 不會被忽略，讀取中變動會拒絕結果。限制來自
[SQLite URI 文件](https://www.sqlite.org/uri.html) 對 immutable 的鎖定／變更偵測語義。
服務沒有因此取得新的來源寫入或網路權限。

未登記分片按小時目錄增量清點，使用原生 `scandir` 串流而不一次建立數百萬個 Path。
未完成小時保存已讀取檔名，完成後壓成計數。一般快照的冷 footer 工作預算為 2 秒；
它不包含其他來源 metadata、序列化與鎖定等待，因此不是整份快照的硬性 2 秒 SLA。
來源 capture 選取身分改變會使對應審核快取失效。

加速初次清點可使用同一個原 owner 的維護模式；只推進 metadata 快取，
正常定時器持續負責正式發布，不重算所有其他來源的特徵清冊：

```bash
source scripts/runtime_env.sh
run_fintech_python scripts/snapshot_data_refresh_services.py \
  --tick-audit-only --tick-audit-seconds 30
```

一般與維護模式共用檔案鎖，避免兩個 read/build/write 互相覆蓋。
超過 2 秒的人工審核使用最多 2 個 spawn worker；一般監控不啟動這個 pool。
本機 2,048 個同檔 footer 測量：1 worker 2.4004 秒、2 worker 0.8557 秒、
4 worker 0.8012 秒，三者同為 43,433 列，包含啟動時間。
另一次 threaded Arrow 測試在 2 threads 發生 exit 139，因此未採用 thread pool。
這些數字只證明 footer 工作，沒有宣稱提高來源 API 吞吐量。

HTTP 僅投影快照：`/data-monitor/api/ticks` 支援來源、市場、種類、合約搜尋及分頁，
每頁最多 100 列。摘要不內嵌全部合約，網頁只有展開、可見時才輪詢；
分頁遇到 revision 改變會重置，避免混合兩次清點。
日期使用 `earliest_date/latest_date`，不再與報價欄位 `last` 共用名稱。
沿用既有登入、報價權限、JSON 清理與唯讀邊界，沒有傳原始資料或金鑰到瀏覽器。

## 驗收證據

- 分類、非空相異日期、鏡像去重、冷 footer 續跑、不可讀檔、WAL 失效、
  只讀 SQLite、spawn 計數、HTTP 唯讀投影及分頁篩選已有語義測試。
- 共用監控、provider、feature 分頁／shard 與 runtime journal 的回歸結果見清點收據。
  本次共用回歸為 526 passed；最後分類／唯讀路由／維護入口的針對性測試為 30 passed。
- [正式頁面瀏覽器驗收](../artifacts/data_quality/tick_inventory_2026-10-25/browser_acceptance.json)
  包含 1440／390 寬度、來源限制、FinMind 真實日期與 JWFR2 合約搜尋；
  無水平溢出或頁面 JavaScript 錯誤。此為 CPU 2D 介面驗收，不是 GPU 測量。
- 只重載共用唯讀網站。下載、交易與錄製 owner 的 PID／InvocationID 比對另存收據。
  程序還在運作不是歷史齊全或來源持續更新的證明。
