v15 為本輪曾測試的候選，加入兩項可分辨的變更，交易環境和 log-utility 目標不變：

1. `futures_notional_score_coordinates: true`：用既有因果特徵
   `r = known_initial_margin / prior_notional`，將既有分數 `s` 變成 `r*s`
   再送入 `score_entmax_log_cash`。單一合約近零時，
   `q = E/IM * (r*s)/(1+abs(r*s))`，故 `dq/ds = E/prior_notional`，
   不再因保證金率低而把初期分數導數放大成 `E/IM`。
   多合約仍有原本的 entmax 配置耦合。這是優化座標的改變，不是 v14 帳務錯誤；
   因 `r>0` 且不中心化分數，可用 `s=z/r` 表達原本任何分數 `z`，
   不新增模型參數、部位上限或固定現金比例，正常非零初始化也保留。
2. 驗證 loss 停滯時使用既有 ReduceLROnPlateau 降低學習率；初值 1e−4，
   patience 10、factor 0.5、最低 1e−6。修正舊程式未指定的絕對改善門檻與
   最低 LR：例如 best=−1、threshold=.001，相對門檻會把 −.9999 誤認為
   改善；絕對門檻則要求小於 −1.001。v14 使用 warmup-cosine，因此這個
   缺陷不是 v14 過擬合的成因。新 scheduler contract 會拒絕不相容 resume。
   門檻語意依 [PyTorch 2.11 文件](https://docs.pytorch.org/docs/2.11/generated/torch.optim.lr_scheduler.ReduceLROnPlateau.html)。

## v12 後段不穩定與 v13 梯度修正

使用者的 v12 已完成 232 epochs，驗證選第 132 輪；其後連續 100 次未改善。
232 輪訓練帳戶均存活，沒有零梯度批次。訓練 loss 在第 96 輪達
−0.605725，最後退為 −0.557952；裁切前梯度範數在第 132 輪為
11,626，第 232 輪為 69,792。因此不能把後段全部解釋為典型的
「訓練持續變好、驗證變差」過擬合。

已確認的缺陷是：forward 遵守成交容量與部位上限，backward 卻對
已飽和的容量使用 identity STE，且沒有重現部位上限。以單一合約表示：
模型要求 `q* = w E / IM`，實際成交為既有可行集合內的 `q`，
帳戶遞迴為 `E_next = E + q ΔP − costs`。當 `q` 已固定在硬上限，
增加 `w` 或 `E` 不會增倉；舊 backward 卻保留 `dq/dw = E/IM`、
`dq/dE = w/IM`，把不存在的複利增倉一路乘回先前決策。

確定性反例中，初始本金 1,000、IM 100、部位上限 5 口、128 天每天
每口獲利 10。`w=0.89` 與 `0.91` 的精確報酬完全相同，但舊梯度對共享
權重的合計為 **14,419.38**；修正後為數值零（約 −5.8e−10）。成交容量
飽和也有同樣反例。v13 讓 backward 通過原本的容量截斷及同一套部位投影，
僅對離散合約／整口取整使用 STE。小於一口仍有學習訊號；同群組上限內
向不同合約調整配置仍有梯度。沒有新增現金下限、槓桿上限或候選否決機制。

用 v12 驗證選定的第 132 輪模型及完整 3,430 訓練日重播，更新前的
train loss 與原第 133 輪**逐位相同**（−0.6027663946），裁切前模型梯度
範數由 **12,430.916 降為 11.342**。三個凍結實際批次的所有公開 forward
欄位也逐位一致；其中第一個批次的輸出梯度範數由 4,021.387 降為 0.400963，
梯度方向 cosine 僅 0.018。這解釋為何原有 `grad_clip_norm: 1` 不足以
修好問題：縮小錯誤向量並不改正方向。

48 組隨機／對抗案例、6 組飽和反例及 3 個真實 batch 都通過與保存的 v12
程式逐欄 forward 精確比較。診斷與來源程式保存在
`artifacts/analysis/tw_futures_v12_stability_20260928/`，可重跑 `verify.py`；
主要證據為 `verification.json`、`matched_gradient_comparison.json`。
570 項回歸測試通過；原先條件略過的 GPU 路徑另以 CUDA opt-in 執行，
37 項通過（其中一項為 CPU runtime 設定檢查）。strict CUDA 零警告、零失敗，
兩個三輪 DDP run 的完成產物稽核均為 `lifecycle_ok: true`。
STE 仍是有偏估計，這些反例與測試不構成非凸訓練的收斂定理。相關背景：
[Understanding Straight-Through Estimator](https://arxiv.org/abs/1903.05662)；
該文的特定模型理論不能直接外推成交易模型的保證。

三輪雙 GPU／BF16 診斷以 v12 第 132 輪權重與新 optimizer 開始：
train loss 為 `−0.602766 → −0.603118 → −0.603566`，裁切前梯度範數
為 `11.342 → 5.044 → 8.626`；val loss 為
`−1.607129 → −1.625931 → −1.542535`。全部訓練日、每輪驗證／測試、
最終回測及 artifact lifecycle 通過。選第 2 輪後的 2026 測試仍為
**−2.93% 報酬、Sharpe −0.026、MDD 80.20%**，尚未達成策略目標。
後續兩輪使用新 Adam 狀態，不是 v12 原 optimizer 軌跡的公平績效對照。

另以 v13 正常非零初始化完成三輪完整雙 GPU 流程：train loss
`0.514534 → 0.510294 → 0.468553`，val loss
`−0.598402 → −0.614089 → −0.614843`，梯度範數約 21–22，無訓練違約
或零梯度批次。單元測試另確認第一個動作有實際口數，head 與 backbone
都收到有限、非零梯度。此三輪 smoke 的 2026 報酬為 +123.75%、
Sharpe 1.000、MDD 55.12%，僅報酬優於 benchmark；風險仍未達標。
它完成了工程驗證，不是正式千輪收斂或穩健策略的證明。證據為
`fresh_smoke/`、`fresh_audit.json`；正式 v13 尚未啟動。

泛化問題仍需分開評估：v12 所選模型在 2025 報酬 +372.42%、MDD 37.91%，
但 2026 報酬 −21.20%、MDD 83.31%。單一年份驗證改善不能保證下一個市場
期間，log utility 也沒有直接約束 MDD。此次先修正已證實的梯度缺陷，
不調整目標函數、不依 2026 挑參數、不再加入策略規則。若修正後仍發生
「訓練改善、驗證惡化」，再以訓練內不同連續年份檢驗過擬合，及評估
只依驗證停滯降低 learning rate；不要把縮短早停或抹平曲線當成根治。

## v11 後段 loss 跳躍的已確認問題

v11 共 203 輪，第 103 輪由驗證選中，之後 100 次驗證未改善而停止。
有 45 輪訓練記錄在同一個零起算 row 232 發生 reason 4；第一次是
第 96 輪，train loss 從上一輪 −0.606507 跳到 +0.857651。
圖形使用 symlog，沒有對原始 loss 平滑。

從第 103 輪模型重播並捕捉真正的訓練 batch，確認兩項錯誤：

1. 歷史部位上限由 8,000 降到 6,000 標準口時，舊程式把超限當成
   全帳戶保證金代沖銷。已減到 731 標準口、帳面權益約 106.38 億元，
   仍因未全數清空而判違約。v12 保留原本較保守的絕對口數合併上限，
   先接受模型在容量內的減倉，再按各合約實際可平口數分攤剩餘超額，
   整口向上取整；不清空無關群組。仍超限才 fail closed。
   同一批請求重播後留有 5,996.25 標準口，符合 6,000 上限，整個 batch
   沒有違約。費稅、容量、買賣方向、保證金追繳全平與到期義務照常執行。
2. 真實違約後帳戶已停止，舊 backward 卻每一天重新注入影子本金。
   在兩日違約案例後補 126 天有利行情，forward 報酬不變，合計收益梯度
   卻從 −84.5045 變成 +41.4892，反而鼓勵造成違約的方向。
   v12 保留違約當日的恢復梯度，違約之後不再產生梯度；修正後均為
   −84.5045。跨 batch 已違約的帳戶也遵守此規則。

log utility 是 `−252 / T × Σ log(E_t / E_(t−1))`。真正違約時，有限值
報酬下限會造成離散跳躍；不應為了圖形平滑而刪除它。此次修正的是
錯誤違約判定與不一致的學習訊號，沒有加回 benchmark 門檻、候選接受、
固定現金比例或新停止條件。STE 仍是離散成交的近似梯度，不保證每步改善。

重播工具與證據：
`artifacts/analysis/tw_futures_v11_absorbing_gradient_20260928/verify.py`、
`verification.json`。其中 gradient-only 測試保存原 forward 並逐欄精確比較；
帳務修正會有意改變超限日期的成交與違約結果，不能宣稱全 run 前向不變。
歷史 checkpoint 權重可用於明示的診斷移植，但不等同舊帳務重播。

驗證：407 項回歸測試通過，另行啟用 CUDA 圖形重播與動態限額測試通過；
32 組未涉及超限改制的隨機／對抗案例，公開 forward 欄位精確一致。
兩個真實 batch 的 gradient-only 對照確認，違約後梯度 L1 分別從
21.91965／150.88322 降為零，違約前梯度不變。

## 訓練與測試各自的用途

  不以 benchmark 回撤否決參數更新。
- 驗證：2025；保留原本驗證 log loss 選 checkpoint 與早停的規則。
- 測試：2026 上述期間，只做結果比較。此期間先前已用於研究，不能稱為未看過的樣本。

## 已合併的修正

1. v13 使用既有最後一層 action head 的正常非零初始化；v6–v12 的
   全現金零初始化僅保留於歷史設定，不新增模型參數。
2. 期貨連續特徵使用只在訓練資料擬合的 RMS 尺度，避免成交量、未平倉量與
   報酬率的單位差異主導訊號。
3. 使用實體合約的 backward，保留整口數、容量、保證金、到期結算、費稅與
   強制平倉失敗規則。真實前向帳戶沒有改成連續口數或無限制成交。
4. 每個完整訓練軌跡執行一次 AdamW 更新；v11 不再額外審核候選 loss 或
   benchmark 回撤，也不再投影／反射更新方向。

`epoch_curve.jsonl` 保留原始 loss。歷史 v7–v10 的候選搜尋程式與
`policy_step_trials.jsonl` 保留作為研究對照，v11 不啟用該搜尋。
