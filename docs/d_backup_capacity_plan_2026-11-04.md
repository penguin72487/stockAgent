# D 槽備份容量：實測與規劃

範圍是 2026-11-04 台北時間約 21:02 的固定觀測與規劃。最新分工為：
C／WSL 執行服務，E 保存工作資料及待封裝資料，D 保存本機備份，lab203
中繼至 NAS 作異地備份。E 複製完成、D 原檔還原、NAS 配對驗收與 C 回收
是四件不同的事。

## 目前有多少空間

當時 D 的容量為 4,000,768,323,584 bytes（3.64 TiB），已用約 3.61 TiB，
物理剩餘約 31.08 GiB。D 根目錄也有使用者其他資料，不能把全部已用量
稱為 StockAgent 備份。空閒量已低於一般公開傳輸所設定的 64 GiB 保留量，也
低於特定已登錄私人備份的 32 GiB 寫入底線。這些條件分屬不同 owner，
不表示所有工作都可使用 32 GiB 底線；實際准入要重新量測並依原工作
契約檢查暫存、併發寫入和接收端。使用者已說明原本的保留是給備份用，
不應再多算一份相同預留，但目前物理容量本身仍不足以通過這些底線。

讀取一個固定的公開備份 catalog 世代，清冊中的檔案**邏輯大小**如下：

| 分類 | 清冊筆數 | 邏輯大小 |
| --- | ---: | ---: |
| 內容定址 blob | 52,465 | 1,142.64 GiB |
| 小檔 pack | 42,798 | 607.38 GiB |
| inventory | 4,586 | 6.42 GiB |
| manifest、head 等 metadata | 9,158 | 3.66 GiB |

前三類共約 1.72 TiB；這是 catalog 已列入內容的邏輯量，不是整個 D 槽
的已配置空間，也未含所有私有或其他目錄。不能用 3.61 TiB 減去此數
宣稱剩餘量就是可刪資料。catalog 中標示 `unreferenced_cold_object` 的
484 個物件約 63.35 GiB **已包含在上表物件內**；該標記不是可刪或可還原
證明。逐代版本、排程、pin、執行中工作及 NAS 證據尚須由原 owner 對帳。
固定世代與計數保留在 E 的
`verify/d-catalog-storage-plan-20261104-v1.json`。

`D:\\stockagent-immutable-lake` 有超過 200 個 `.export-*` 名稱。抽查的
兩組檔案在不同目錄之間有相同 inode，且硬連結數分別為 207 與 167；
目錄邏輯量相加會重複計數。原 export 在建立目錄之後才可能留下 prepared
journal，因此沒有 journal 也不足以證明目錄閒置。必須按實體檔案身分、
最後一個連結、原 owner 鎖和恢復流程逐項核對，才能預估可回收空間。

## Binance 實測：變更檔大小不是新增備份大小

固定 E staging 世代共 2,398 檔、約 135.30 GiB；與 2026-10-23 D 固定
快照的 inventory 比較，1,230 檔的路徑、長度和 SHA 相同。其餘 1,168 檔
（含 6 個 E 新檔）約 122.97 GiB，是**變更檔的原始邏輯大小**。

依該資料集現有的 8 MiB 固定分塊契約，實際讀取並完整 SHA 核對其中
574 個超過 8 MiB 的 E 檔案，再以區塊 SHA 和長度對照固定 D manifest：

| 項目 | 測得量 |
| --- | ---: |
| 574 個大型變更檔邏輯大小 | 121.44 GiB |
| 固定 D manifest 中已有相同 SHA／長度的區塊引用 | 103.50 GiB，約 85.2% |
| 不在該 manifest 的去重後不同區塊 | 17.94 GiB |
| 其餘 594 個小檔原始邏輯大小 | 1.53 GiB |

上述 17.94 GiB 再比對該次 109,007 列的固定公開 catalog，未發現額外
可重用 blob。此 catalog 的 scope 不等於完整 D，且這次沒有讀回 D 物件；
它可能漏掉 catalog scope 外或觀測後新增的物件，D 物件本身也可能損壞。
小檔的實際 pack 壓縮率、物件是否已存在、檔案系統配置、manifest、
暫存和同時寫入尚未量測。因此若先以小檔原始大小示意，約
`17.94 + 1.53 = 19.47 GiB` 只是一個**規劃情境**，不是確定成本、上下限
或 D 剩餘空間能容納的證明。E 世代之後的來源新鮮度也未重新核對。

固定快照 ID、manifest SHA、統計及限制記在 E 的
`verify/binance-d-delta-estimate-20261104-v1.json`；程式
`scripts/estimate_e_stage_backup_delta.py` 只讀取來源、固定清冊和 catalog，
不建立 D 備份、不授權回收。這次 574 檔逐檔核對約 246 秒，已結束。

示意容量算式是：

```text
可准入所需空間 = 預估新增唯一物件 + 小檔 pack + metadata
               + 該 owner 同時保留的最大暫存與其他在途寫入
               + 該 owner 適用的剩餘空間底線
```

例如若某公開工作確實適用 64 GiB 底線，並假設上面的 19.47 GiB 情境
且先忽略其他額外空間，則需約 83.47 GiB 空閒；相對當時 31.08 GiB
仍需約 52.39 GiB。這只是用來說明預算，不是准入結論；不能把私人
32 GiB 契約套用到 Binance 公開傳輸。

## 建議架構

1. **以 E 為工作來源、D 為備份、NAS 為獨立備份。** D 的同一段內容只
   保存一份受內容雜湊定址的物件；各快照保存自己的 manifest，指向共享
   物件。版本不同並不等於完整重存，已被保留版本引用的歷史也不可覆寫。
   D 和 NAS 須分別完成物件／原檔讀回和配對驗收。
2. **從源頭限制改寫範圍。** 在各來源語義允許時，依 provider、產品、
   日期和必要的版本將歷史切成穩定分區；每日只新增或改寫受影響的分區。
   保留原始值、來源、發布時間與修訂歷史。不同交易所或不同來源的資料
   不因名稱相似就合併；來源本身已壓縮的 ZIP／Parquet 不預設再壓一次。
3. **小檔依版本封閉後打包，保留可查索引。** 在 E 批次形成有界 pack，
   優先順序寫與順序讀；按索引恢復單檔或小範圍，並維持獨立 SHA 與
   manifest。對壓縮成本、隨機抽讀、完整還原及目的磁碟的實際吞吐做比較，
   再選大小與 codec；不僅比較壓縮率。D 原有原子提交可能需要同檔案系統
   的最小暫存，不能直接跨磁碟移動 `.export` 後假設 rename／hardlink 語義不變。
4. **固定分塊與內容定義分塊按實測選擇。** 現有 writer 支援固定分塊及
   `fastcdc-v1`。固定分塊對本例可重用 85.2%；插入導致後續位移的資料
   才值得測試內容定義分塊。新格式需先比較 CPU、空間、索引、完整還原與
   中斷恢復，保留原快照與讀取合約，不直接重寫全部既有歷史。
5. **分開保留正本、備份、可重建成果和暫存。** 必要原始資料及修訂
   按來源政策保留，當沖帳本與執行中服務資料保持原 owner；可重建 panel、
   舊效能測試與暫存另列。使用者已授權清理舊效能驗證資料，但仍需確認
   精確範圍、正在使用的程序及 hardlink，並量測實際釋放量。

## 執行次序與未決事項

1. 原 owner 以 NTFS 實體 file ID、allocated bytes、連結數、版本、pin 和
   實際開啟程序完成 D 分類清冊；對系統、使用者及 StockAgent 範圍分開報告。
   catalog 的 63.35 GiB 和 `.export-*` 只能列為候選，不能直接當回收量。
2. 先處理可確認無引用的已授權測試副本；其餘物件須完成精確來源、D／NAS
   獨立恢復、歷史版本與程序使用證明，再由原 owner 逐批回收並實測增量。
3. 沿現有排程在 E 生成及讀回固定資料世代，以實際內容定址結果與容量
   計畫准入 D；執行過程保留可中斷續跑 journal，並讓當沖服務優先。
4. lab203 readiness 更新與每批 NAS 獨立驗收仍需現有接收 owner 回報。
   總剩餘量、每日淨成長與全數完成時間需要所有資料集的去重後增量、
   實際成長觀測、可回收量及接收吞吐後才能計算，不由單一 Binance 樣本外推。
