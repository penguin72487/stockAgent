## 修正的原因與機制

| 原因 | 修正 | 驗證 |
| --- | --- | --- |
| Tick 整批結束才寫進度，面板落後真實下載 | 每個實際嘗試前後寫小型 checkpoint，市場彙總最多約每分鐘更新 | 現行 11:36:58 checkpoint，公開頁實際顯示正在抓 Tick |
| 掃到已下載或不適用候選，仍先查帳號配額 | 先檢查日期、股票生命週期、收據與當期重試，再做實際請求守門 | 已快取和不適用候選的語意測試：配額 API 呼叫 0 |
| 每次候選都重新檢查千餘鍵的一般待辦 | 同帳號鎖內每分鐘重新檢查一次，到期一般追新優先交接 | 11:35 到期鍵在 11:35:23 開始、隨後完成；11:35:47 已恢復 Tick |
| 請求尚未完成就推進持久化游標，外部終止可能漏抓 | 活躍請求期間僅保存請求前游標；完成收據後才提交 | SIGTERM 模擬中斷後，續抓相同候選且不重複已驗證收據 |
| 下載結束後另等 15 分鐘才派工 | 1 分鐘 timer 搭配純本機 `ExecCondition`；無待辦不啟動重型抓取 | 已部署 timer 與條件檢查，來源未知或過舊證據仍可啟動恢復 |
| 已結束的一般程序或受安全隔離的活躍 Tick 被誤判 | 檢查 PID 起始 tick、開機識別及執行時間；隱藏 kernel sysctl 時用當次開機與精確 PID 世代驗證 | 保留 `ProtectProc=invisible`、`ProcSubset=pid`；部署頁確認 Tick 為活躍 |
| 一般資料舊收據讓正在新增 Tick 的面板顯示暫無新收據 | Tick 保存最近成功時間，活動狀態採實際 owner 與新收據 | 公開狀態為 active，下載階段為 tick；不暴露私有程序識別 |
| 來源問題讓可執行階段完成時間全部卡住 | 本輪查核、下一波查核、來源修復與 Tick 全歷史分開 | 2 個來源問題仍可見，不捏造完成時間，不阻塞可執行下載 |
| 同一階段已欠工作與未來波次混用起始時間 | 下一波僅取該波資料鍵的開始及完成時間 | 有舊待辦時，下一波不會被顯示成早於 SDK 到期就開始 |
| 1531 的 13:33 成交使整天分鐘合成失敗 | 有日期規則的收盤驗證，保留原始 13:33 分鐘；只重做本機衍生資料 | 2026-10-02 已產生 20 根分鐘、包含 13:33；合成錯誤由 1 降至 0 |

13:33 暫緩收盤是官方正常交易規則，不應任意刪除，也不能回填成 13:30 的可交易價。
規則自 2012-02-20 生效；13:31、13:32 及 13:34 的異常一般交易時間仍拒收。
[TWSE 交易制度](https://www.twse.com.tw/zh/products/system/trading.html?hl=zh-TW)、
[TPEx 開收盤配套措施](https://www.tpex.org.tw/web/stock/trading/information/information.php?l=zh-tw)。

## 仍不能由本機修好的來源問題

- `dividend_otc:權息`：來源原表有列與欄，但可用觀測值全空。
- `management_change_events:變更交易開始日`：來源欄位全空。

兩者保留來源證據及個別重試，不當作有效資料，不填造數值或發布時間。
其他已取得表可能仍有合理稀疏值、上市前空值或來源歷史缺口；本次沒有宣稱每格皆有值。

FinLab 官方說明盤中歷史仍在補齊，沒有公布本研究股票宇宙全部日期的可得分區總量，
所以候選數不能作全歷史資料分母。日期窗上限為 31 個日曆日，
包含尚未發布的交易日會報錯；現行按股票日保留獨立收據，不把來源未發布當作已抓完。
這次沒有改成盲目整月查詢，也沒有聲稱已達所有資料的理論最高吞吐量。
[FinLab 盤中資料文件](https://finlab.finance/docs/details/intraday/)。
