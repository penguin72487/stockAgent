這些不是統計信賴區間或實際排程承諾。參考情境的可排程處理工作約 18 分鐘，
其餘主要是額度等待及既有交易日開盤保護。逐表模擬配額能否容納，
不能把總大小除以網速就宣稱完成。模型沿用大型整表的下載准入規則，
亦計入重試時間、排程下一次啟動與既有開盤保護。

## 實作與效能

- `scripts/finlab_workload.py`：讀現有目錄、完成收據、嘗試紀錄、原始檔大小、
  Parquet footer 及監控快照。以現行 `_sync_work_plan` 分辨必要待辦與校驗工作。
- `scripts/finlab_arrow_history.py`：抽出共用 `whole_table_reserve_bytes`，
  下載器與估時採同一大型整表准入規則；原下載行為不變。
- `scripts/snapshot_finlab_quota.py`：沿用既有每分鐘工作及帳號樣本，
  追加本機工作量快照。**工作量量測不增加 FinLab API 呼叫**。
- `stockagent/live/finlab_dashboard.py`：公開唯讀欄位白名單，隱藏原始路徑與私密欄位；
  快照逾 180 秒、目錄不一致或未核實時，不提供目前進度比例與完成時間。
- `services/finlab_dashboard/`：流量、耗時與三種筆數各有進度條；
  完成時間附範圍、配額等待及阻塞項目；明細逐鍵顯示資料量、口徑、
  本機大小、重讀大小與條件 ETA。原鍵數只留作清冊檢查。

流量分母來自既有原始物件，不使用「所有表的平均大小」猜大表。
筆數只讀 footer 的列數／null 統計，不掃描完整資料：null 統計缺失就保留未知；
Arrow null 欄位可證明沒有值。快取綁定收據雜湊、inode、size、mtime、ctime
與量測版本，檔案改變才重讀。單次新 footer 量測預算 3 秒；以 flock 防重入、
原子替換快照，讀者不會看到半份 JSON。

首次完成全部 footer 量測約 14.62 秒、1,093 次讀取（一次性初始化）。
後續快取快照約 1 秒、0 次 footer 重讀；11:01 的整個既有帳號取樣加量測工作
CPU 約 1.84 秒、記憶體峰值約 123 MiB。不啟動 GPU 或全表解壓工作。

牆鐘剩餘時間拆成「下載及處理」加「等待配額／排程／開盤保護」；
包含下一次啟動與重試門檻前的排隊等待，確保各項時間可加回總剩餘時間。
