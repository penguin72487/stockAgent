## 三項修復

### 1. 下載入口匯入失敗

直接執行 `scripts/download_finlab_history.py` 時，Python 搜尋路徑始於
`scripts/`，原先 sibling-module fallback 不能解析新共用依賴
`downloader.artifact_io`。systemd 日誌出現 `No module named 'scripts'`，
接著 `No module named 'downloader'`，工作在取得資料之前就終止。

入口現在先從 `__file__` 解析儲存庫根目錄，再使用單一套 canonical imports。
測試從其他工作目錄、Python `-I` 隔離模式執行五個 FinLab 入口的 `--help`，
不靠使用者 shell 的 `PYTHONPATH`，不登入或呼叫 API。

### 2. 每個逐鍵工作重算全部既有檔案雜湊

逐鍵獨立程序原本用於隔離 SDK 記憶體，予以保留。但新完整性檢查的程序內
快取無法跨程序共用，每次選一個鍵都再次雜湊約 4.38 GB 的全部檔案；
每分鐘監控也重做相同運算。

新增本機正向驗證 memo，綁定驗證版本、絕對路徑、device、inode、size、
mtime、ctime、收據筆數、大小、SHA-256 及 UTC 日。檔案／收據一變就重驗，
跨日也重驗；只有完成完整 SHA 驗證的成功結果可進入 memo。
footer-only 驗證不能產生完整性證據。壞／缺快取回退到實際檔案驗證。

memo 只由背景產生者原子落地；公開頁面仍只讀，不寫 cache、不呼叫 FinLab。
併發 cache 寫入若遺失其他程序的新項目，只會多驗證一次，不能讓壞檔案通過。
工作量也改用相同的有效收據判定，損壞檔案不再以存在與否冒充已取得。

### 3. 收據並行更新使 ETA 誤報未排程

09:44 的保存快照中，`fundamental_features:淨值成長率` 的來源查核時間為
01:44:01.205811 UTC，比快照基準 01:44:01.198256 晚約 7.6 毫秒。
原排程把它當已查新、面板卻保留待辦，造成整體 `unscheduled_work`、ETA 消失。

`refresh_due` 現在對晚於評估基準或缺時區的收據維持待辦，直到下一次評估；
不把未來證據當成當時已完成。新增毫秒級並行、一天未來時間及 naive datetime
案例，確保此情況不再因排程／面板分歧而產生未排程狀態。
