# 儲存回收等待狀態與每分鐘接續

本次修復針對「已驗收傳輸副本回收」及其他等待卡片；保留原備份、發布、
回收程序及全部來源、NAS、引用、容量與中斷恢復檢查。

## 根因與處理

1. BackupStream 的兩批已驗收傳輸副本，共 11,814,669,969 logical bytes，
   因三個來源 blob 的 ctime 改變而持續拒絕回收。原始 inode、大小、mtime
   均吻合。原先只記 `SnapshotError`，網站無法說明具體原因。
2. 另一個 immutable-lake GC 的中斷交易涉及 3,614 個來源檔案，其中 3,610 個
   也是 ctime 改變；原始 inode、大小、mtime 吻合。這是獨立交易，不能借用
   BackupStream 的完成數或執行狀態。
3. 網站將 BackupStream 回收錯接到 lake GC 的服務狀態；短週期 timer 的時間
   在下一分鐘刷新前已經過期，投影又把它丟棄，造成下次排程看似不存在。

兩個回收實作均保留原收據，只有 ctime／允許的重新掛載 device 變化才進入
新鮮完整 SHA 核對。inode、大小或 mtime 改變仍拒絕；內容 SHA 不符、讀取時
世代改變仍拒絕。後續使用本次完整 SHA 觀察到的來源世代，重新執行原有
來源、精確副本集合、NAS 配對驗收、引用與 unlink 檢查。沒有以忽略 ctime、
直接修改舊收據或服務仍在執行作為刪除授權。

額外唯讀診斷顯示，部分 ctime 變動發生於早期清點至實際讀取之間；當次已讀
1,070 個檔案未看到 SHA 不符，但這不等於全部 3,614 個已驗證。因此完整讀取
使用緊鄰讀取前的新鮮世代，仍要求 inode、大小與 mtime 符合，並要求完整 SHA
與讀取後世代吻合；不能拿數秒前的清點時間當作這次讀取的起點。

BackupStream 原排程已於台北時間 22:22:39 完成兩批回收；刪除來源與 NAS
物件數均為零。上述 11.0 GiB 是傳輸副本 logical bytes，不能算成 WSL 的
實際 allocated 回收量。

## 三個不同時間

| 網站資訊 | 來源與意義 |
| --- | --- |
| 本次檢查、下次資訊檢查 | 原背景 observer 每 60 秒讀小型狀態；頁面每 60 秒重新讀快照。 |
| 原工作進度、下次原排程檢查／預定重試 | 保留原工作收據及原 timer／重試佇列時間。已到 timer 時間仍顯示等待最新回報。 |
| 固定範圍驗收與完成時間 | 原驗收證據；不因刷新網站而改寫。沒有速度樣本不填完成 ETA。 |

每張卡片對應原執行者；獨立的 `transport_gc_state_root` 讀取 lake GC 的小型
`transport-gc-status.json`。observer 不讀大型傳輸 ledger、不呼叫完整還原、
不重新排一條刪除流程。正在執行的 owner 不被中斷。

驗證器修正後使用明確的 `immutable_transport_full_sha_read_generation_v2`
合約。舊失敗可取得一次優先的普通驗證機會，不繼承舊驗證器的一小時等待；
先保存原錯誤、重試時間與次數，再執行原 NAS／來源／副本／引用檢查。同版的
後續失敗維持原 600–3,600 秒退避，每分鐘觀測不會反覆重新雜湊。等待時保留
最近失敗原因，不因 timer 再次輪詢而清成泛用文字。

等待卡片直接顯示安全原因碼對應的文字，例如來源世代不同、程序仍引用、
來源缺件、副本改變、同步尚未收斂或等待原排程重試。私有例外 detail 留在
原程序診斷，不傳檔案路徑與原始錯誤到瀏覽器。斷線或觀測過期會停止宣稱
目前正在自動接續；恢復讀取後由原快照重新判斷。

## 驗證與界線

- 回收測試覆蓋 ctime 漂移的完整 SHA、同大小且回復 mtime 的損毀資料，以及
  SHA 後再次變動的來源；後兩者保留來源與傳輸副本。
- 狀態測試覆蓋兩個 GC 的 owner 分離、獨立狀態根、過期短 timer、每分鐘觀測
  不刷新來源計數、不提前重試、不將未知總量當完成，以及公開欄位白名單。
- 瀏覽器驗證使用既有 Chromium CPU 2D profile，分桌面與手機測試每分鐘刷新、
  等待原因變更、自動接續、斷線降級及排程展開。
- 新版回收／重試／狀態焦點回歸有 223 項通過、7 項依既有環境條件跳過；
  最後的 GC 優先重試補充測試另有 18 項通過。網站／observer／runtime 在原
  fintech 環境有 182 項通過；29 項瀏覽器情境通過。數量有重疊，不加總。
- 最初把網站測試放到精簡控制環境，有三項因缺少 NumPy 失敗；改在原 fintech
  網站環境驗證。保留初始失敗，不替控制環境安裝不相關套件。

逐次測試、原始診斷、服務連續性與部署後讀回證據保存在
`artifacts/storage_layout/storage-waiting-recovery-final-20261101.json` 及其引用檔案。
本輪不代表全部歷史遷移完成，也不授權跳過其他來源、pin 或 NAS 驗收問題。

## 預估完成時間

封存的小檔案分成少數大分組；同一組處理期間，組數可能長時間不變。
原 publisher 已逐檔回報 `files_hashed` 及實際處理 bytes。網站保留原分組進度條，
在完整 routing 完成後，以同一 packing 階段的逐檔／bytes 差分估計「剩餘來源內容
核對時間」，採兩種工作量中較慢的預估。這個時間不含後續封存提交、冷庫還原
及 NAS 驗收；不能借用前一階段的速度。計數解釋另有版本綁定，舊樣本不沿用。

immutable-lake GC 的原執行者另回報 dry-run／apply 各自的清點、來源與傳輸 SHA、
精確集合、引用、unlink 及空目錄階段。計數來自實際完成的操作；正常每兩秒
至多寫一次小型狀態，另保留階段轉換／完成事件，沒有為了 ETA 重讀 payload。
每分鐘 observer 仍只讀小型狀態，不呼叫驗證或刪除。

目前批次與可執行佇列另使用最近 48 批成功完整流程的實測耗時，按來源／catalog
種類及驗證合約分開，以檔數和 bytes 的較大工作量比例調整可變耗時，保留固定
NAS admission 時間。串行佇列加上原 timer 的 30 秒接續間隔；不同節點的並行
工作不直接相加。最快／較慢範圍為歷史預測範圍的 0.5／2 倍，只是經驗範圍，
不是統計信賴區間或保證上界；不足三個樣本明示可信度低。

清冊缺少工作量、沒有同類樣本、等待失敗條件修復或遠端未提供速率時，保留
待估原因及原重試時間。未知工作若位於串行佇列前方，整列不填絕對完成時間。
重試批次與目前可執行佇列分開列示；沒有候選只表示當前回收佇列為空，不當作
全系統驗收完成。估計超時保留原時間並明示超時；資訊刷新不延後重置倒數。
實際部署讀回另發現舊逐階段估計使用 `now + remaining`，重讀同一份來源收據
也讓完成時間後移。現在改以原進度觀測時間計算絕對 deadline；只重讀 metadata
時倒數減少、目標時間不變，過期則停止宣稱仍可於原時間內完成。

網站前方摘要顯示已有估計的工作與其最晚時間，以及仍待估／被阻擋數量。
每張卡片分開顯示本階段、目前批次、可執行佇列與正式驗收完成時間。
新 helper 已納入 worker 程式身分與後續 relay 工具包的明確依賴；沒有重新發布
遠端 frozen package，也沒有為載入遙測而重啟正在執行的 lifecycle worker。

ETA 修正的狀態／網站回歸最後有 188 項通過；包含完整回收與複寫的控制環境
回歸有 138 項通過、7 項依原環境條件跳過，GC／模型另包含在先前 210 項狀態
回歸中，數量有重疊。最初將 lifecycle 測試放在 fintech，因缺少 `temporalio`
有 9 項失敗；失敗收據保留，改由既有 lakehouse-control 環境驗證，未新增套件。
桌面／手機 31 項瀏覽器情境與另兩份實際公開頁面讀回均通過。部署後三次
每分鐘觀測前進，並實際命中同一來源收據的 deadline 不變檢查；首次三次讀回
揭露舊倒數漂移的證據亦保留，沒有覆寫為修復後的結果。證據索引為
`artifacts/storage_layout/storage-eta-acceptance-20261101.json`。
